# 01. Terraform 보안 서비스 반영 현황

이 문서는 현재 `wonny-sec` Terraform 코드에
**어떤 AWS 보안 서비스와 보안 기능이 실제로 반영되어 있는지** 정리한 문서입니다.

---

## 1. 한눈에 보기

| 보안 서비스 / 기능  | Terraform 반영 | 현재 구현 수준                                          |
| ------------------- | -------------: | -------------------------------------------------------- |
| AWS WAF             |             ✅ | 쇼핑몰/관리자 Web ACL 생성, ALB 연결, 로그 저장         |
| GuardDuty           |             ✅ | Detector 활성화                                         |
| Inspector           |             ✅ | EC2 + ECR 스캔 활성화                                   |
| IAM Access Analyzer |             ✅ | Account Analyzer 생성                                   |
| Security Hub        |             ✅ | Security Hub 활성화 + 기본 Standards                    |
| EventBridge         |             ✅ | Security Hub Finding 이벤트 → Lambda A / 5분 스케줄 2개 |
| SNS                 |             ❌ | 구독자가 없어 제거함 (Lambda A가 DB 저장 + 대시보드 표시로 대체) |
| CloudTrail          |             ✅ | AWS API 활동 로그를 S3에 저장                           |
| VPC Flow Logs       |             ✅ | VPC 트래픽을 CloudWatch Logs에 기록                     |
| CloudWatch Logs     |             ✅ | WAF Logs / VPC Flow Logs / Lambda 로그 저장             |
| KMS                 |             ✅ | 쇼핑몰용 / 보안결과용 키, 로그 암호화 정책              |
| Secrets Manager     |             ✅ | 쇼핑 DB / 보안 DB 자격증명 저장                         |
| Security Group      |             ✅ | ALB, EC2, DB, Dashboard, Lambda용 SG                    |
| SSM Session Manager |             ✅ | EC2 SSH 22번 없이 관리할 수 있는 IAM 권한               |
| Shield Standard     |             ⚪ | AWS 기본 보호이므로 별도 활성화 리소스 없음             |
| Macie               |             ❌ | 최신 7개 시나리오에 직접 매핑되지 않아 제외             |
| Lambda A            |             ✅ | Security Hub Finding → security_events 저장, 실제 운영 중 |
| Lambda B            |             ✅ | WAF 로그 분석(5분마다) → security_events 저장, 실제 운영 중 |
| Lambda C            |             ✅ | CloudWatch 지표(5분마다) → service_metrics 저장, 대시보드 하단 패널 |
| Lambda Remediation  |             ✅ | 대시보드 승인 시 WAF 차단/SSM 재시작/Access Key 비활성화 |

## 2. AWS WAF

### 현재 Terraform에 반영된 것

쇼핑몰용 WAF와 관리자용 WAF를 각각 생성합니다.

```text
Internet
  ├─ Shopping WAF → Shopping ALB
  └─ Admin WAF    → Admin ALB
```

쇼핑몰 WAF에는 현재 다음 규칙이 포함되어 있습니다.

```text
AWSManagedRulesCommonRuleSet
AWSManagedRulesSQLiRuleSet
Rate Limit
```

관리자 WAF에는 다음 규칙이 포함되어 있습니다.

```text
AWSManagedRulesCommonRuleSet
Admin Rate Limit
```

WAF 로그는 CloudWatch Logs에 저장됩니다.

### 7개 시나리오와의 관계

| 시나리오           | 현재 반영 수준                                             |
| ------------------ | ------------------------------------------------------------ |
| SQL Injection      | ✅ SQLi Managed Rule 차단 + Lambda B가 로그 재분류/기록     |
| XSS                | ✅ Common Rule Set 탐지 + Lambda B 분류                     |
| 디렉토리 탐색      | ✅ Lambda B가 IP별 서로 다른 경로 요청 수로 판정            |
| 로그인 무차별 대입 | ✅ Rate Limit + Lambda B가 로그인 경로 실패 횟수로 판정     |

WAF는 1차 차단/로깅을 담당하고, `modules/lambda_b`(`waf.py`)가
WAF 로그를 5분마다 분석해서 4개 시나리오를 실제로 분류하고
`security_events`에 저장 → 대시보드에 표시하는 것까지 연결되어 있습니다.

## 3. GuardDuty

Terraform에서 GuardDuty Detector를 활성화합니다.

현재 구성 목적:

```text
포트 스캔
탈취 자격증명 관련 이상행위
```

GuardDuty는 AWS 관리형 탐지 서비스이므로
별도의 "포트스캔 규칙"을 Terraform에서 직접 만드는 구조가 아닙니다.

현재 상태:

```text
GuardDuty 활성화                    ✅
실제 공격 발생                      별도
Finding 발생 확인                    별도
Finding을 Security DB에 저장         아직 미구현
```

---

## 4. Inspector

Terraform에서 Amazon Inspector를 활성화하고
다음 리소스 타입을 검사하도록 구성합니다.

```text
EC2
ECR
```

프로젝트의 7개 시나리오 중:

```text
취약 컨테이너 이미지
```

시나리오에 직접 연결됩니다.

현재 상태:

```text
Inspector 활성화         ✅
EC2 스캔                 ✅
ECR 스캔                 ✅
취약 이미지 업로드/검증   별도
Finding DB 저장          아직 미구현
```

## 5. IAM Access Analyzer

Account 단위 Access Analyzer를 생성합니다.

목적은 외부 접근 가능성이나 과도한 접근 경로를 분석하는 것입니다.

프로젝트에서는:

```text
탈취 자격증명(퇴사자)
```

시나리오에서 GuardDuty의 보조 증빙 역할로 사용합니다.

현재 상태:

```text
Analyzer 생성             ✅
분석 기능 활성화          ✅
퇴사자 전용 커스텀 판정    아직 미구현
```

---

## 6. Security Hub

Terraform에서 Security Hub를 활성화하고
기본 Security Standards를 사용합니다.

현재 역할:

```text
GuardDuty
Inspector
Access Analyzer
      ↓
Security Hub
      ↓
EventBridge
      ↓
Lambda A
      ↓
Security MySQL (security_events)
      ↓
Dashboard 표시
```

현재 Terraform에는 다음까지 반영되어 있습니다.

```text
Security Hub 활성화              ✅
기본 Standards                   ✅
Security Hub EventBridge Rule    ✅
Lambda A (Finding → DB 저장)     ✅
```

SNS를 통한 이메일 알림은 구독자가 없어 제거했습니다 (`modules/security/security_services.tf`).
Finding을 실제로 확인하는 경로는 이메일이 아니라 **대시보드 화면**입니다.

## 7. EventBridge

EventBridge 규칙은 총 3개입니다.

```text
wonny-sec-securityhub-findings   Security Hub Finding 발생 시 → Lambda A
wonny-sec-lambda-b-schedule      5분마다 → Lambda B (WAF 로그 분석)
wonny-sec-lambda-c-schedule      5분마다 → Lambda C (인프라 지표 수집)
```

예전에는 `securityhub-findings` 규칙이 SNS로도 발행했지만,
구독자가 없어 SNS Topic/Policy/Target을 모두 제거하고
지금은 Lambda A 타깃 하나만 남아 있습니다.

현재 상태:

```text
EventBridge Rule (Security Hub)   ✅
EventBridge Rule (Lambda B 스케줄) ✅
EventBridge Rule (Lambda C 스케줄) ✅
SNS Topic                         ❌ (제거됨)
```

## 8. CloudTrail

CloudTrail을 생성해 AWS API 활동 기록을
보안 로그 S3 버킷에 저장합니다.

```text
AWS API 활동
    ↓
CloudTrail
    ↓
Security Log S3
```

CloudTrail은 공격을 직접 판정하는 서비스라기보다
감사 및 보안 분석을 위한 데이터 소스 역할입니다.

현재 상태:

```text
CloudTrail 생성           ✅
S3 저장                   ✅
Log File Validation       ✅
KMS 기반 보호             ✅
```

---

## 9. VPC Flow Logs

VPC 전체 트래픽에 대해 Flow Logs를 활성화합니다.

```text
VPC Network Traffic
        ↓
VPC Flow Logs
        ↓
CloudWatch Logs
```

현재 설정은:

```text
traffic_type = ALL
```

이므로 ACCEPT / REJECT 흐름을 모두 기록합니다.

프로젝트에서는 포트 스캔 분석 등의
보조 네트워크 데이터로 활용할 수 있습니다.

---

## 10. CloudWatch Logs

현재 CloudWatch Logs에 저장되는 주요 로그:

```text
Shopping WAF Logs
Admin WAF Logs
VPC Flow Logs
```

각 Log Group은 보안용 고객 관리형 KMS Key를 사용합니다.

KMS Key Policy에서는 CloudWatch Logs 서비스에 필요한 권한을 부여하고,
Encryption Context를 이용해 프로젝트의 특정 Log Group만
해당 키를 사용할 수 있도록 제한합니다.

---

## 11. KMS

Terraform에서 KMS Key를 2개 생성합니다.

```text
Shopping Data KMS Key
Security Data KMS Key
```

Security KMS Key는 다음에 사용됩니다.

```text
CloudWatch Logs
Security Log S3
SNS
Security 관련 EBS / Secrets
```

현재 수정본에는 다음 서비스에 필요한 Key Policy를 포함합니다.

```text
CloudWatch Logs
CloudTrail
```

---

## 12. Secrets Manager

두 DB의 자격증명을 분리해서 관리합니다.

```text
Shopping DB Secret
Security DB Secret
```

권한 역시 역할별로 분리합니다.

```text
Flask App / Shopping DB
        ↓
Shopping DB Secret

Dashboard / Security DB
        ↓
Security DB Secret
```

---

## 13. Security Group / SSM

### Security Group

서비스 간 필요한 경로만 허용하도록 분리합니다.

```text
Shopping ALB → K3s/nginx
K3s/nginx   → Flask App
Flask App   → Shopping MySQL

Admin ALB   → Dashboard
Dashboard   → Security MySQL
```

### SSM

EC2에 SSH 22번 인바운드를 열지 않고
SSM Session Manager를 사용할 수 있도록
각 EC2용 IAM Role에 다음 정책을 연결합니다.

```text
AmazonSSMManagedInstanceCore
```

---

## 14. Shield Standard

Shield Standard는 AWS에서 기본으로 제공되는 보호이므로
Terraform에서 별도의 `enable` 리소스를 만들지 않습니다.

따라서:

```text
Terraform resource 생성   ❌
AWS 기본 보호             ✅
```

로 이해하면 됩니다.

## 15. Macie

Macie는 최신 7개 보안 시나리오에 직접 매핑되지 않아
현재 Terraform에서는 제외했습니다.

```text
Macie Terraform Resource  ❌
```

## 16. Lambda 구성 (전부 구현/운영 중)

### Lambda A — `modules/lambda_a`

```text
Security Hub
     ↓
EventBridge (securityhub_findings)
     ↓
Lambda A
     ↓
Security MySQL (security_events)
```

이벤트 기반, 스케줄 없음. GuardDuty/Inspector/Access Analyzer의 Finding이
Security Hub로 모이면 그때마다 실행됩니다.

### Lambda B — `modules/lambda_b`

```text
Shop/Admin WAF Logs (CloudWatch Logs)
     ↓
Lambda B (5분마다, EventBridge 스케줄)
     ↓
SQLi / XSS / 디렉토리 탐색 / 무차별대입 패턴 분석
     ↓
Security MySQL (security_events)
```

### Lambda C — `modules/lambda_c`

```text
CloudWatch 지표 (CPU/메모리/ALB 지연·처리량·에러율/타깃 헬스)
     ↓
Lambda C (5분마다, EventBridge 스케줄)
     ↓
Security MySQL (service_metrics)
     ↓
대시보드 하단 인프라 상태 패널
```

보안 시나리오가 아니라 운영 지표(가용성)를 보여주기 위한 용도입니다.

### Lambda Remediation — `modules/lambda_remediation`

```text
대시보드에서 관리자가 조치 승인
      ↓
Flask 백엔드가 Lambda 직접 호출 (boto3 invoke, 스케줄/이벤트 트리거 없음)
      ↓
Lambda Remediation
      ↓
WAF IP 차단 / SSM으로 서버 재시작 / IAM Access Key 비활성화
```

할 수 있는 조치는 이 3가지로 제한되어 있고, 그 외 권한은 IAM에서 주지 않습니다.

## 17. 현재 7개 보안 시나리오 구현 수준

| 번호 | 시나리오             | 담당 서비스                       | 현재 상태                                     |
| ---- | -------------------- | ---------------------------------- | ----------------------------------------------- |
| 1    | SQL Injection        | WAF + Lambda B                     | ✅ 탐지 → DB 저장 → 대시보드 표시             |
| 2    | XSS                  | WAF + Lambda B                     | ✅ 탐지 → DB 저장 → 대시보드 표시             |
| 3    | 디렉토리 탐색        | WAF + Lambda B                     | ✅ 탐지 → DB 저장 → 대시보드 표시             |
| 4    | 로그인 무차별 대입   | WAF + Lambda B                     | ✅ 탐지 → DB 저장 → 대시보드 표시             |
| 5    | 포트 스캔            | GuardDuty + Lambda A               | ✅ Finding → DB 저장 → 대시보드 표시          |
| 6    | 탈취 자격증명        | GuardDuty + Access Analyzer + Lambda A | ✅ Finding → DB 저장 → 대시보드 표시      |
| 7    | 취약 컨테이너 이미지 | Inspector + Lambda A               | ✅ Finding → DB 저장 → 대시보드 표시          |

7개 시나리오 전부 탐지 → `security_events` 저장 → 대시보드 표시까지 end-to-end로 연결되어 있고,
실제로 Access Analyzer 등에서 발생한 실 Finding이 대시보드에 뜨는 것까지 확인했습니다.
남은 건 각 시나리오를 의도적으로 재현하는 공격 시나리오(Attack Lab)와 세부 판정 룰 고도화입니다.

## 18. 현재 보안 구현 위치

```text
[보안 인프라 + 수집 Lambda + Dashboard]
WAF / GuardDuty / Inspector / Access Analyzer / Security Hub
CloudTrail / VPC Flow Logs / CloudWatch
KMS / Secrets Manager

Security Hub → EventBridge → Lambda A → security_events
WAF Logs     → (5분) Lambda B → security_events
CloudWatch   → (5분) Lambda C → service_metrics

security_events / service_metrics → Dashboard(Flask+React) 표시
Dashboard 승인 → Lambda Remediation → WAF 차단 / SSM 재시작 / Access Key 비활성화

        ✅ 여기까지 실제 운영 중 (EC2에 배포되어 24시간 동작)

            ↓

[남은 것]
Attack Lab (7개 시나리오 의도적 재현 도구)
shop-app을 k3s에 실제 배포 (현재 k3s/shop-app EC2 둘 다 자리표시자 nginx만 떠 있음)
GitHub Actions로 배포 자동화 (현재는 SSM 수동 배포)
```

---

## 19. 한 문장 정리

현재 Terraform은

> **AWS 보안 서비스 생성부터 Lambda A/B/C를 이용한 Finding/로그/지표 수집, Security MySQL 저장, Dashboard 표시, 승인 기반 자동 조치(Lambda Remediation)까지 end-to-end로 구축되어 실제 운영 중이며, 남은 것은 공격 시나리오 재현 도구(Attack Lab)와 shop-app의 실제 배포, 배포 자동화(GitHub Actions)다.**
